## 性能（重要正面结果）

    CPU  LAT 2037 ms   RSS 5665 MB
    HTP  LAT  274 ms   RSS  221 MB
    => HTP 比 CPU 快 7.4 倍
消掉 scatter 之后，HTP 不只是数值恢复，性能也回来了（此前 1L 全尺寸广播版本是 5860ms）。

## 误差特征：逐层累积（fp16 特征，非算子缺陷）

    cur_k per-layer (HTP vs CPU): min=0.999553 max=1.000000  bad_layers=none
    cur_v per-layer (HTP vs CPU): min=0.996420 max=1.000000  bad_layers=[9..27]
    HTP all-zero layers: none

- 误差随层数单调累积，后段层（9..27）略大
- 无某一层突然崩掉、无全零层 -> 不像 lowering bug，像 fp16 执行精度
- 旁证：同一 fp16 权重，CPU backend cos=1.0000000（CPU 路径实际按 fp32 累加），
  DSP 真按 fp16 算 -> 误差只出现在 HTP

## G1 已确认成立的部分
1. 三个 workaround 从 1L 泛化到 28L：无崩溃、无全零、无层间爆点
2. ScatterND = 0；kv 覆写语义正确（cur_k/cur_v 全 28 层都有值且与 CPU 高度一致）
3. HTP 性能反超 CPU 7.4 倍

## 尚需确认（决定是否放行整链）
- 功能后果判定：用 HTP 的 hidden_states 跑 codec_head，看 code0 是否仍等于 torch/CPU 的值
  （PC 侧直接调 codec_head 的那次尝试未成功喂入输入，结果不可用，需在设备侧正规跑一次）
- 若 code0 与 CPU/torch 一致 -> 0.9983 对功能无影响，可直接进 G2/G3 与整链
- 若 code0 不一致 -> 需要 precision 处理（如后续把关键路径改 fp32，或接受 CPU 兜底 codec_head）
